# Final Sync Verification Checklist (10-15 min)

## الهدف

تأكيد أن الإصلاحات الأخيرة تعمل فعليًا على الجهاز:

- التصنيفات تظهر وتنعكس داخل الفورم.
- المرفقات والعائلة/المتوفين تظهر بعد المزامنة.
- دورة أرقام الملفات (الحجز والاستهلاك والمزامنة) سليمة.
- عدادات المزامنة والكتابة تعكس الواقع.

---

## 1) تجهيز سريع قبل الاختبار

1. افتح التطبيق على جهاز حقيقي (أو Emulator مستقر).
2. تأكد أنك Logged-in (حتى لا تكون كل الطلبات 401).
3. افتح شاشة المزامنة.
4. تأكد من وجود اتصال إنترنت.

معيار النجاح:

- لا توجد رسالة Unauthenticated أثناء عملية Sync.

---

## 2) اختبار التصنيفات (Taxonomy)

1. من شاشة المزامنة نفّذ مزامنة التصنيفات.
2. راقب بطاقة تشخيص التصنيفات:
   - وقت آخر مزامنة.
   - أي رسالة خطأ.
3. افتح فورم مستفيد (إضافة جديد + تعديل موجود).
4. تحقق أن Dropdowns ليست فارغة (الجنس، الفئة، الحالة الاجتماعية، المحافظة...).
5. غيّر قيمة واحفظ، ثم افتح نفس السجل ثانية.

معيار النجاح:

- القيم المختارة تبقى ثابتة بعد الحفظ وإعادة الفتح.
- لا يحدث رجوع لقيم نصية غير مطابقة (labels بدل codes).

إذا فشل:

- التقط Screenshot لبطاقة تشخيص التصنيفات.
- سجّل نص errorCategory + errorContext من نتيجة آخر مزامنة.

---

## 3) اختبار Sync Down للعلاقات (Attachments/Family/Dead)

1. من شاشة المزامنة نفّذ Sync Down كامل.
2. راقب بطاقة نتيجة المزامنة:
   - payload counters: beneficiaries / attachments / family_members / dead_people.
   - write counters: inserted / updated / skipped لكل كيان.
3. افتح مستفيد معروف أنه يملك مرفقات وعائلة/متوفين على السيرفر.
4. داخل الفورم:
   - تبويب المرفقات: تأكد ظهور العناصر.
   - تبويب أفراد العائلة: تأكد ظهور الأحياء والمتوفين.

معيار النجاح:

- وجود بيانات فعلية في UI تتوافق مع counters (أو على الأقل ليست صفرًا عندما السيرفر يعيد بيانات).

إذا فشل:

- راقب هل counters تشير إلى skipped مرتفع جدًا.
- هذا يشير غالبًا لمشكلة ربط الهوية بين local id وserver/file id.

---

## 4) اختبار File IDs lifecycle

0. مباشرة بعد تسجيل الدخول، افتح شاشة المزامنة وتأكد أن تشخيص File IDs محدث (آخر حجز/آخر مزامنة استخدام).
   - الهدف: التحقق من أن post-login orchestration نفذ تلقائيًا.

1. في شاشة المزامنة راقب بطاقة تشخيص أرقام الملفات:
   - available_count
   - used_unsynced_count
   - active_reservation_id
   - active_reservation_remaining
   - last_reserved_at
   - last_synced_at
2. أنشئ مستفيد جديد واحفظه.
3. تحقق أن available_count يقل.
4. نفّذ Sync Up.
5. تحقق أن used_unsynced_count ينخفض وأن last_synced_at يتحدث.

معيار النجاح:

- يتم استهلاك رقم ملف محليًا ثم مزامنته دون أخطاء.

إذا فشل:

- راقب errorCategory (auth/validation/route/network).
- validation غالبًا يعني payload غير مطابق (خصوصًا reservation_id/used_count).

---

## 5) اختبار التحمل السريع (Mini Regression)

نفّذ بالتسلسل:

1. Sync Taxonomy
2. Sync Down
3. فتح فورم مستفيد + تعديل بسيط + حفظ
4. Sync Up
5. إعادة فتح نفس السجل

معيار النجاح:

- لا crash.
- لا اختفاء بيانات بعد إعادة الفتح.
- لا تناقض واضح بين counters وUI.

---

## 6) توثيق نتيجة الجولة

سجل هذه القيم بعد الجولة:

- وقت الاختبار.
- رقم/اسم المستفيد المختبر.
- payload counters.
- write counters.
- حالة File ID diagnostics.
- هل ظهرت المرفقات؟ نعم/لا.
- هل ظهرت العائلة/المتوفين؟ نعم/لا.
- هل التصنيفات ظلت ثابتة بعد الحفظ؟ نعم/لا.

---

## 7) قرار الإغلاق

أغلق الإصلاح كـ Ready فقط إذا:

- كل البنود الأساسية أعلاه ناجحة.
- لا توجد أخطاء حرجة في بطاقة النتيجة.
- لا يوجد skipped غير طبيعي بدون تفسير.

إذا بقيت مشكلة واحدة:

- افتح issue واحد محدد لكل محور (Taxonomy / Related Entities / File IDs) مع لقطة counters والنص الكامل للخطأ.
